SIHANDAL V2 — CODEBASE EXPLANATION
====================================

1. WHAT THIS APP IS
-------------------
SIHANDAL V2 ("Sistem Informasi Keuangan Daerah") is a regional financial
information system for Indonesian local government agencies (OPD — Organisasi
Perangkat Daerah). Each OPD tracks its budget (pagu), revenue (penerimaan),
expenditure (pengeluaran), cash position (posisi kas), program/activity budget
(program-kegiatan), and submits formal fund requests (permintaan dana) that flow
through an approval workflow managed by admins.

The app is a classic server-rendered Laravel application, not an SPA. Pages are
Blade views enhanced with Alpine.js; styling is Tailwind CSS v4. There is no
separate frontend framework and no public JSON API.

4. DATA MODEL OVERVIEW
----------------------
Budget hierarchy (pagu lives ONLY at the leaf and is derived upwards):

  Program -> Kegiatan -> SubKegiatan -> Belanja (rekening + sumber dana + pagu)

Program is global (programs.opd_id is nullable); OPD scoping for programs is
resolved through Kegiatan.opd_id. SumberDana and Rekening are master data with
no financial state.

Core leaf: Belanja carries the money state for the approval flow:
  availablePagu() = pagu - realisasi - dana_di_commit

Key tables:
  - belanjas:             pagu, realisasi, dana_di_commit (pagu money state)
  - penerimaans:          master revenue definition (opd, rekening, sumber dana,
                          tahun anggaran, target). NO persisting realisasi.
  - transaksi_penerimaans: actual revenue receipts (realisasi, tanggal,
                          nomor_registrasi). Each master's realization is
                          computed as the SUM of its transactions.
  - transaksi_penerimaan_bkus: optional nested BKU detail rows (nomor_bku,
                          tanggal_bku, nilai, rekening). 0..N per transaction.
  - pengeluarans:         expenditure rows, FK to kegiatan/sub/belanja
  - posisi_kas:           snapshot (saldo_awal +- changes)
  - permintaan_danas:     fund requests + status workflow
  - persetujuans:         per-approver decision rows
  - transfer_danas:       fund transfers with status workflow
  - document_counters:    per-(type, year) counters backing auto document
                          numbers (type, year, last_value)
  - audit_logs:           Auditable trait snapshots
  - notifications:        in-app database notifications
  - tahun_anggarans:      fiscal years (only one active at a time)

Recurring master rows keep denormalized text columns (e.g. nama_sumber_dana)
for legacy data display/backfill; FKs are the source of truth.

5. FINANCIAL INVARIANTS
-----------------------
These rules are enforced in code and covered by dedicated tests
(BelanjaIntegrityTest, FinancialIntegrityTest, PermintaanDanaCommitTest):

PAGU                           realisasi + dana_di_commit <= pagu, always.
BELANJA.COMMIT                 moves pagu -> dana_di_commit, throws if it would
                               exceed availablePagu().
BELANJA.RELEASE                moves dana_di_commit -> available (floor at 0).
BELANJA.REALIZE                cannot exceed availablePagu(); reduces the
                               remaining dana_di_commit accordingly.
REALISASI MONOTONIC            Update* requests prevent reducing an already
                               recorded realisasi.
BKU TOTAL                      IF any BKU detail rows exist for a transaction,
                               their total MUST equal that transaction's
                               realisasi.
REKENG TYPE                    rekenings.tipe in (kas|pendapatan|belanja):
                               Penerimaan requires 'pendapatan', Pengeluaran
                               requires 'belanja', 'kas' is accepted nowhere.
                               Enforced in Form Requests on create AND update.
NOMOR REGISTRASI               unique per receipt; auto-generated (see #7).
NESTED FK CHECKS               Pengeluaran must reference sub_kegiatan under the
                               chosen kegiatan, and belanja under that
                               sub_kegiatan (cross-ID consistency validated).
DELETE GUARDS                  A SubKegiatan/Program cannot be deleted while
                               its belanjas still hold dana_di_commit > 0 or
                               realisasi > 0.

6. MONEY WORKFLOWS
------------------
PERMINTAAN DANA (request flow)
  draft -> menunggu -> disetujui / ditolak  (per-OPD admins approve)
  On SUBMIT:     the PermintaanDana row is locked (lockForUpdate) and re-checked
                 so the same request cannot be committed twice.
  On APPROVE:    PersetujuanController locks the permintaan, re-checks status,
                 then Belanja::commit(amount). Failures (e.g. over-budget,
                 already processed) return back()->withErrors, never a 500.
  On REJECT:     releases nothing, records the rejection.
  PERMINTAAN DANA has no money state itself; the money lives on Belanja.

TRANSFER DANA  draft -> selesai style status workflow, OPD-scoped.

TRANSFER PENERIMAAN
  store(): validates via TransaksiPenerimaanRequest, generates nomor_registrasi
  (see #7), inserts the transaksi + optional BKU rows inside one
  DB::transaction. update() may freely add/remove BKU rows but never touches
  nomor_registrasi (immutable after creation).

7. AUTO-GENERATED DOCUMENT NUMBERS
----------------------------------
PD-XXXX/YYYY and TF-XXXX/YYYY have been generated per fiscal year for a while.
Transaksi penerimaan numbers (REG-XXXXX/YYYY) now also are — via
app/Services/DocumentNumberService.php:

  next(string $type, string $prefix, int $year): string

  - runs inside DB::transaction
  - locks the (type, year) counter row with lockForUpdate
  - reads last_value+1, writes it back, returns
    "{prefix}-{str_pad(next,5,'0',LEFT)}/{year}"
  - the very first allocation of a year is a race: the insert may throw a
    unique (type, year) QueryException; it then re-reads the locked counter and
    increments — so concurrent first-allocations converge on one number
  - the DB unique index on transaksi_penerimaans.nomor_registrasi is a second,
    hard guarantee against duplicates (column is nullable so legacy imported
    rows without numbers are unaffected)

nomor_registrasi is derived from the transaction's tanggal year (fallback:
current year) and is NOT user-settable: creating requests drop it in
transaksi-penerimaan/create, edit shows it as read-only, and store() ignores
any submitted value.

nomor_bku on the nested BKU rows remains MANUAL (per user decision).

8. ARCHITECTURE PATTERNS
------------------------
1) Standard MVC: Form Request -> Controller -> Eloquent model -> Blade view;
   Alpine.js on top. All flows go through named routes.
2) Money invariants as domain methods on Belanja (commit/releaseCommit/realize)
   instead of scattered controller arithmetic.
3) Transactional multi-step writes (submit/approve/reject/import/build) inside
   DB::transaction, with lockForUpdate on the contended row to prevent
   double-commit/double-realize races.
4) Computed money: revenue realization and rekening saldo are read-time
   SQL aggregates (single source of truth = transactions). persentase /
   saldo_akhir are persisted on write for cheap display.
5) OPD multi-tenancy through base Controller helpers
   (Controller.php: applyOpdScope, userOpds, authorizeOpdRecord): OPD users
   only ever see/affect their own rows; admins see everything.
6) Separate read-only report controllers (LaporanPenerimaanController,
   LaporanPengeluaranController, LaporanPosisiKasController,
   RekapPermintaanDanaController) with streaming CSV export.
7) Shared validation via traits and one TransaksiPenerimaanRequest servicing
   both store and update paths.
8) Auditable trait -> audit_logs diff snapshots on model writes.
9) In-app notifications via Laravel's database channel.

9. IMPORT PIPELINE
------------------
php artisan app:import-sihandal <sumberdana.csv> <penerimaan.xlsx>
  --dry-run   validate only, persist nothing
  --fresh     wipe + reimport
  --force     skip confirmation
Run by SihandalImportService inside a transaction; inserts the normalized
hierarchy and reconciles totals; it is idempotent so db:seed can run it safely.

11. KNOWN/DEFERRED ITEMS
------------------------
- AuditLog rows are written per model write; bulk imports flood audit_logs.
- Some index/report queries still fetch full tables (get()) rather than
  paginate — acceptable at current data volume.
- PD/TF numbering uses a max()+1 scan; only REG uses a dedicated counter table.
