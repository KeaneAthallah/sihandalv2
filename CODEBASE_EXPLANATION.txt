================================================================================
                                SIHANDAL V2 - CODEBASE EXPLANATION
================================================================================

Sihandal (Sistem Informasi Keuangan Daerah) is a Regional Financial Information
System — a web application for managing the finances of Indonesian local /
regional government agencies (OPD — Organisasi Perangkat Daerah).

It lets each government agency (OPD) track budgets (pagu), revenue (penerimaan),
expenditure (pengeluaran), cash positions (posisi kas), programs/activities, and
submit formal fund requests (permintaan dana) that flow through an approval
workflow (draft -> menunggu -> disetujui/ditolak) managed by admins.

The data is organized around a strict government budget hierarchy:
  OPD -> Dinas -> Unit            (organizational structure, optional)
  OPD -> UPT(s)                   (technical implementation units)
  Program -> Kegiatan -> SubKegiatan -> Belanja (rekening + sumber dana + pagu)

Budget (pagu) is aggregated upward from the leaves: Belanja -> SubKegiatan ->
Kegiatan -> Program -> OPD. Master data (Sumber Dana, Rekening, Program, Kegiatan,
Sub Kegiatan) is referenced by foreign keys rather than free text, while legacy
denormalized text columns (kode/nama_sub_kegiatan, kode/nama_rekening,
nama_sumber_dana) are kept for backward compatibility and display only.

  sub_kegiatans
    kegiatan_id, opd_id, kode_sub_kegiatan, nama_sub_kegiatan
    pagu, realisasi, persentase
    source_file, source_identifier
    belanjas() -> hasMany Belanja;  hasManyThrough leaves
    Aggregation: sum of descendant Belanja pagu/realisasi (pagu PERSISTED by importer).

  belanjas
    sub_kegiatan_id, rekening_id (FK), sumber_dana_id (FK), opd_id,
    tahun_anggaran_id, pagu, realisasi, dana_di_commit
    source_file, source_row, source_identifier  (unique (source_file, source_row))
    FUND MANAGEMENT METHODS (core money logic, Auditable trait):
      availablePagu()   = pagu - realisasi - dana_di_commit
      commit(x)         locks x into dana_di_commit (throws if insufficient)
      releaseCommit(x)  frees committed funds back into availability
      realize(x)        moves committed -> realized and decrements dana_di_commit
                         (throws if it exceeds available pagu)
    Belanja is the budget LEAF in the hierarchy: pagu is entered here and
    aggregated upward (SubKegiatan -> Kegiatan -> Program -> OPD), not entered
    manually at parent levels.

  rekenings
    kode (unique), nama, tipe ('kas'|'pendapatan'|'belanja')
    source_file, source_identifier
    Referenced by FK from Belanja, Penerimaan, Pengeluaran, PermintaanDana.
    MASTER/REFERENCE data only — no persisted `saldo`. Balances are DERIVED from
    financial transactions via Rekening->totalPenerimaan($opdId),
    totalPengeluaran($opdId) and saldo($opdId) (sum of transaksi_penerimaans.
    realisasi minus sum of pengeluarans.realisasi), all DB-aggregated. The
    rekening-kas list computes these per OPD in grouped queries.
    TIPE ENFORCEMENT (server-side): a master Penerimaan may only reference a
    rekening with tipe = 'pendapatan' and a Pengeluaran may only reference a
    rekening with tipe = 'belanja'. Enforced in the Store/Update Form Requests
    (Rule::exists('rekenings','id')->where(tipe)) with Indonesian error messages,
    and reflected in the create/edit dropdowns (edit dropdowns also merge the
    currently-selected rekening so legacy rows keep rendering). 'kas' rekenings
    are accepted by neither module.

================================================================================
                          FUND REQUEST WORKFLOW (CORE)
================================================================================

  1. create        -> PermintaanDana created with status 'draft', unique
                       nomor_permintaan "PD-0001/2026" (auto-incrementing),
                       linked to a SumberDana and optionally a Kegiatan /
                       SubKegiatan / Belanja / Rekening via foreign keys.
  2. submit        -> PermintaanDanaController::submit, inside a DB::transaction:
                       - verifies status is 'draft'
                       - if the request targets a Belanja (belanja_id set),
                         verifies jumlah <= Belanja::availablePagu() and calls
                         Belanja::commit() to lock the funds
                       - sets status 'menunggu'
                       - notifies every admin (database notification)
  3. setujui       -> PersetujuanController::setujui (admin only, transactional):
                       - requires status 'menunggu'
                       - Belanja::realize() moves committed -> realized (when a
                         belanja is linked)
                       - sets status 'disetujui' + tanggal_disetujui
                       - records a Persetujuan row
                       - notifies the requesting OPD's users
  4. tolak         -> PersetujuanController::tolak (admin only, transactional):
                       - requires status 'menunggu'
                       - Belanja::releaseCommit() frees locked funds (when a
                         belanja is linked)
                       - sets status 'ditolak'
                       - records a Persetujuan row
                       - notifies the requesting OPD's users

  Editing/Deleting a request is only allowed while it is 'draft' or 'ditolak'
  (never once funds have been committed to a 'menunggu' request).

================================================================================
                            AUTH & AUTHORIZATION
================================================================================

  - Authentication: Laravel Breeze (email/password, verification, password
    reset). Routes in routes/auth.php.
  - Two roles:
      admin  -> sees all OPD data; manages users; approves/rejects requests;
                manages fiscal years.
      opd    -> sees only own OPD's data; creates/edits own records; submits
                requests; remembers requests are not self-approvable.
  - Middleware:
      'verified' -> email must be verified (wraps the whole main group)
      'admin'    -> EnsureUserIsAdmin, aborts 403 unless user->isAdmin()

================================================================================
                          OPD-SCOPED MULTI-TENANCY
================================================================================

  The base Controller provides three reusable helpers used by every data
  controller so OPD users only ever touch their own rows:

    applyOpdScope(Builder $query, ?User $user, $column = 'opd_id'): Builder
        For a non-admin, adds ->where($column, $user->opd_id). Admins pass thru.

    userOpds(?User $user): Collection
        Returns the user's single OPD (non-admin) or all OPDs (admin) — used to
        populate OPD filter dropdowns.

    authorizeOpdRecord(Model $record, ?User $user, $column = 'opd_id'): void
        abort(403) if a non-admin tries to access another OPD's record.

  The dashboard route (routes/web.php) uses the same pattern inline via a
  closure ($opdScope) to scope every aggregate query to the user's OPD.

================================================================================
                            ARCHITECTURE PATTERNS
================================================================================

  1. Standard MVC: form-request validation -> controller -> Eloquent model ->
     Blade view. No separate frontend framework; server-rendered pages enhanced
     with Alpine.js for modals, filters, and interactivity.

  2. Fund locking with Belanja domain methods (availablePagu / commit /
     releaseCommit / realize). Belanja is the budget leaf in the hierarchy; these
     methods encapsulate the money invariants and throw exceptions when a request
     exceeds an item's available budget. The same method names remain on
     SumberDana for standalone (non-Belanja) fund-source tracking.

  3. Transactional multi-step operations: submit / setujui / tolak and the
     CSV importer run inside DB::transaction to keep state consistent (e.g. the
     permintaan status change and the belanja commit are atomic).

  4. Auto-generated identifiers: nomor_permintaan and nomor_transfer are
     generated as sequential "PD-XXXX/YYYY" / "TF-XXXX/YYYY" strings per year.

  5. Computed fields persisted on write: persentase is recomputed wherever
     realisasi/target/pagu change; saldo_akhir = saldo_awal + penerimaan -
     pengeluaran. Exceptions computed on read (never stored): penerimaan
     realization (realisasi = SUM of transaksi_penerimaans, persentase target-safe,
     tanggal = latest transaction) and Rekening cash balance (saldo = total
     penerimaan - total pengeluaran, DB-aggregated, OPD-scoped) so master/reference
     data stays the single source of truth while financial state lives in
     transactions.

  6. Shared validation via a trait: ValidatesPermintaanDana is used by both
     StorePermintaanDanaRequest and UpdatePermintaanDanaRequest to guarantee
     identical business rules (including cross-OPD validation).

  7. Automatic audit trail: the Auditable trait hooks Eloquent created/updated/
     deleted events and writes diff snapshots (old/new values, IP, user agent)
     to audit_logs. Used by the hierarchy budget models (Belanja, etc.) and the
     money modules.

  8. In-app notifications: PermintaanDanaNotification (database channel)
     keeps admins informed of new submissions and OPD users of approvals/
     rejections. NotificationController manages read state.

  9. Separate read/report controllers: each money module keeps a focused,
     read-only report controller (Laporan*/Rekap*) with a streaming CSV export
     endpoint, keeping read paths independent of CRUD.

  10. Reusable Blade component library (~23 components): card, stat-card,
      chart-card, status-badge, priority-badge, filter-bar, page-header,
      progress-card, alert, modal, timeline, text-input, input-label,
      input-error, dropdown, primary/secondary/danger buttons, app-layout,
      guest-layout. A @layer components CSS design system in resources/css/
      app.css (.card, .btn-*, .table-*, .badge, .empty-state, .icon-btn, etc.)
      backs these for a consistent government-SaaS look.

  11. Centralized theme: Tailwind CSS 4 semantic tokens — primary deep blue
      (#0F4C81), surface gray (#F5F7FB), success/warning/danger/info palettes,
      Instrument Sans font.

  12. Performance indexes: a dedicated migration adds composite indexes on the
      hot query paths (OPD-scoped, status-filtered queries).

  13. Hierarchy-driven budget aggregation: pagu/realisasi are entered only at
      the Belanja leaf (Program -> Kegiatan -> SubKegiatan -> Belanja) and
      derived upward through model helper methods (Kegiatan::paguSubKegiatan,
      Opd::paguBelanja, etc.) rather than being hand-entered at parent levels.
      Master data (Dinas, Unit, UPT, Sumber Dana, Rekening, Program, Kegiatan,
      Sub Kegiatan) is referenced via foreign keys; legacy denormalized text
      columns (kode/nama_sub_kegiatan, kode/nama_rekening, nama_sumber_dana)
      are retained solely for backfill and display.

  14. Server-side cross-OPD protection: form requests force a non-admin user's
      own opd_id before validation (e.g. StoreKegiatanRequest::
      prepareForValidation) and validate that submitted master-data FKs belong
      to the user's OPD, preventing one OPD from attaching another OPD's
      records.

  15. Server-side rekening-tipe business rules: Store*/Update* Penerimaan and
      Pengeluaran Form Requests constrain rekening_id with
      Rule::exists('rekenings','id')->where(tipe) so a master Penerimaan can
      only ever reference a 'pendapatan' rekening and a Pengeluaran only a
      'belanja' rekening ('kas' is accepted by neither — this also blocks a
      Penerimaan master referencing a 'belanja' rekening and vice versa). The
      validator's after hook rewrites any rekening_id failure to a single
      Indonesian message ("Rekening penerimaan harus bertipe pendapatan." /
      "Rekening pengeluaran harus bertipe belanja."), so the UI never leaks the
      raw exists-where message. Enforced on BOTH create and update paths; the
      Blade dropdowns mirror it as a UX convenience only. Existing records with
      a legacy-tipe rekening keep rendering on edit (the dropdown merges the
      current rekening back in) and are never silently modified.

================================================================================
                                DATA IMPORT
===============================================================================

  Command:  php artisan app:import-sihandal {csv} {xlsx}
              [--fresh] [--force] [--dry-run]

  Produces a "STEP 29" reconciliation report and exits non-zero if any record
  fails or a sum does not reconcile. Source files live in database/seeders/data/
  (sumberdana26.csv budget, penerimaan-2026.xlsx revenue as a seed on database:seed).

  Imports 100% of both source files into the normalized hierarchy with ZERO
  silent omissions — every source row becomes a record or is reported as FAIL.

  Pipeline (inside ONE DB::transaction):
    Masters      Opd (kode), Program (kode_program, global opd_id=NULL),
                 Rekening (kode), SumberDana (nama_sumber_dana), TahunAnggaran.
    Hierarchy    Kegiatan (kode_kegiatan; program_id from the first 3 dot-segments
                 of KDKEGIATAN — no program column in the CSV), then one
                 SubKegiatan per unique (OPD, kegiatan, sub-kegiatan) key.
    Leaf budget  One Belanja row per CSV row (7,441) at the leaf, so pagu is never
                 double-counted: rekening + sumber dana + pagu.
    Revenue      Every XLSX "Data Input" row is imported (5,844 incl. SALDO AWAL)
                 as a TransaksiPenerimaan grouped under one master Penerimaan per
                 Sumber Dana (province-wide rows get opd_id = NULL). Each import
                 creates master(s) + transaction(s) together. The "REALISASI SMB
                 2026" sheet is a SUMIF summary and is NOT imported.
    Rollups      sub_kegiatans.pagu, kegiatan.pagu and opds.total_pagu are
                 PERSISTED from the leaf sums because existing views read them
                 directly (without recomputation).

  Reconciliation (scoped to the imported source_file):
    Budget:   imported SUM(belanjas.pagu) == SUM(ROUND(PAGU,2)) of the CSV.
    Revenue:  imported SUM(transaksi_penerimaans.realisasi) == SUM(H) of the
              XLSX (the reconciliation rolls up a master's transactions).

  Idempotency (unique keys per row) lets a re-run skip every already-present row:
    Opd->kode, Program->kode_program, Rekening->kode, SumberDana->nama_sumber_dana,
    Kegiatan->(opd_id,kode_kegiatan,tahun_anggaran_id),
    SubKegiatan->(kegiatan_id,kode_sub_kegiatan),
    Belanja->(source_file,source_row); TransaksiPenerimaan->(source_file,source_row).

  Traceability: source_file / source_row / source_identifier on records so any
  imported row is traceable back to its exact origin.

  Idempotent seeding: DatabaseSeeder and SampleDataSeeder are guarded so running
  them again never duplicates the imported dataset.

  Self-contained readers (no PhpSpreadsheet; no approved composer deps):
    XlsxReader — PHP ZipArchive + SimpleXML. Namespace-aware; converts Excel
    serial dates via built-in numFmtIds 14-22/27-36/45-47/50-58 plus custom
    format-code detection. Iterating <xf> elements yields the tag name as the
    loop key (not an index) — use an explicit counter; always read attributes via
    ->attributes(), never array access.

  KNOWN DATA-SHAPE NOTE: Imported Programs are GLOBAL (opd_id = NULL) while OPD
  ownership lives on kegiatan.opd_id. Any OPD-scoped Program drill-down must scope
  through the kegiatan rows (see OpdController::show). A bug that filtered
  Program::where('opd_id', $opd->id) made every OPD detail page empty after import
  and has been fixed to scope via whereHas('kegiatans', opd).
